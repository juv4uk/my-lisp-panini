# Rule Engine Semantics

Цей документ описує семантику Lisp-рушія для оцінки та застосування правил Паніні в машинній моделі `panini-machine-model-v0.1`.

## Основні концепти (The Core Concepts)
У граматиці Паніні правила не працюють як прості лінійні кроки алгоритму. Вони діють скоріше як база знань для рушія символьного логічного виведення (Symbolic Inference Engine), де застосовність правила визначається контекстом (anuvṛtti) та пріоритетами (vipratiṣedha, apavāda).

Ми використовуємо підхід **Rule-Based Graph Rewriting**. 

### 1. Формат Sūtra (Sūtra Format)
Кожна сутра (правило) в Lisp описується макросом `(def-sutra ...)`. 

Синтаксис:
```lisp
(def-sutra <sutra-id> <sutra-text>
  [:context  <list-of-active-adhikaras>]
  :match    <graph-pattern>
  :apply    <transformation-function>)
```
- **`<sutra-id>`**: Наприклад, `3.1.68`. Використовується для встановлення пріоритетів і трасування.
- **`:context`**: Зв'язок з `adhikāra`. Механізм Anuvṛtti автоматично підставляє сюди потрібні маркери або патерни на етапі компіляції правил.
- **`:match`**: Умова застосовності. Це Lisp-pattern, який уніфікується (unifies) з поточним графом деривації.
- **`:apply`**: Дія, яка генерує новий стан графа (state).

### 2. Динаміка контексту (Anuvṛtti Dynamics)
`Anuvṛtti` (наслідування від попередніх сутр) реалізується через **розширення (macro-expansion) патерну `:match`**.

Коли рушій завантажує сутру, він перевіряє, під які `adhikāra` вона підпадає.
Наприклад, правило `3.1.68 "kartari śap"` знаходиться в зоні дії `adhikāra` 3.1.1 `pratyayaḥ`, 3.1.2 `paraś ca`, та 3.1.91 `dhātoḥ`. 

Рушій автоматично (через lexical scoping під час завантаження) додає до `:match` вимогу "знайти dhātu" і до `:apply` вимогу "додати як суфікс (pratyaya) після (para) dhātu".

```lisp
;; Внутрішнє представлення після Anuvṛtti-розгортання:
(def-sutra 3.1.68 "kartari śap"
  :match (action (?d :type 'dhatu) (role (?k :type 'kartr)))
  :apply (insert-after ?d (pratyaya 'Sap)))
```

### 3. Резолюція Конфліктів (Conflict Resolution)
На кожному кроці деривації (`State N`) рушій перевіряє **усі** доступні правила і формує список кандидатів (Conflict Set), патерн `:match` яких відповідає поточному графу.

Якщо кандидатів більше одного, рушій застосовує стратегії вирішення конфліктів Паніні:

1. **Apavāda (Виняток б'є загальне правило)**:
   Якщо патерн `Sutra A` є підмножиною або більш специфічним випадком `Sutra B` (наприклад, правило для конкретного кореня `han` замість загального правила для всіх коренів), застосовується `A`.
2. **Vipratiṣedha (Параграф 1.4.2)**:
   Якщо два правила мають рівну силу (tulyabalavirodha), традиційно вибирається правило, яке йде пізніше в граматиці (пара-сутра).
3. **Nityatva (Незмінність) / Antaraṅgatva (Внутрішній контекст)**:
   Оцінюється відносна залежність правил одне від одного.

У Lisp-моделі рушій спочатку фільтрує список за `Apavāda`, потім сортує залишок за ID (`Vipratiṣedha`), і застосовує переможця для генерації `State N+1`.

### 4. Докази деривації (Proof Traces)
Оскільки деривація — це послідовність незмінних станів (immutable states), система зберігає повний шлях перетворень. Кожен крок посилається на сутру, яка була застосована.

Це дозволяє нам побудувати "Proof-Carrying Derivation IR" — дериваційний лог, який можна верифікувати зовнішніми інструментами, а не просто отримати згенероване слово.
