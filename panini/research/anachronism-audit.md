# Аудит анахронізмів у Panini Foundation

## Мета

Сучасна обчислювальна мова потрібна для проектування, але вона не є
історичним доказом. Цей audit встановлює правила для слів на кшталт `type`,
`tag`, `metadata`, `AST`, `graph`, `rewrite rule`, `VM` та `FPGA`.

## Рівні тверджень

| Маркер | Дозволений зміст | Заборонений стрибок |
| --- | --- | --- |
| `[PANINI]` | Текст sūtra, його scope, anuvṛtti або явно цитований коментар. | Назвати сучасну абстракцію тим, що «визначає» sūtra. |
| `[INTERPRETATION]` | Переказ конкретного дослідника або реалізації з названим джерелом. | Подати інтерпретацію як одностайний історичний факт. |
| `[MY-LISP HYPOTHESIS]` | Проектна модель, її користь і умови перевірки. | Вивести її правильність лише з санскритського терміна. |

## Результати аудиту

### `saMjYA`

| Небезпечна формула | Допустима формула |
| --- | --- |
| `saMjYA = type/tag/class` | `[PANINI]` saMjYA є технічним позначенням; `[MY-LISP HYPOTHESIS]` воно може мати представлення type/tag/edge. |
| `symbol kartf доводить kartf-роль` | SLP1 `kartf` є vocabulary ID; застосування saMjYA вимагає rule-level evidence. |

Підстава для особливої обережності — 1.4.1 регулює відношення між кількома
saMjYA в області свого aDikAra. Отже, глобальний immutable enum не є
нейтральним перекладом поняття.
[Aṣṭādhyāyī 1.4.1](https://ashtadhyayi.com/sutraani/1/4/1)

### `it`

| Небезпечна формула | Допустима формула |
| --- | --- |
| `it = compiler metadata` | `[PANINI]` правила 1.3.2–1.3.8 надають `it`-saMjYA, 1.3.9 задає `lopa`; `[MY-LISP HYPOTHESIS]` provenance-bearing metadata може це представляти. |
| `hidden marker is deleted` | `lopa` має бути trace consequence вже встановленого designation, а не евристика про прихований символ. |

Див. [матрицю it-saMjYA](it-samjna-exhaustive-matrix.md).

### `pratyAhAra`

| Небезпечна формула | Допустима формула |
| --- | --- |
| `pratyAhAra = bitset / ISA opcode` | `[PANINI]` це компактний механізм позначення, обмежений своїм правилом і маркерами; `[MY-LISP HYPOTHESIS]` bitset або opcode може бути експериментом. |
| «компактний» означає «оптимальний для FPGA» | Ефективність у певній архітектурі — окрема емпірична властивість, не висновок з sūtra. |

### `derivation` і rule engine

| Небезпечна формула | Допустима формула |
| --- | --- |
| `Aṣṭādhyāyī is a rewrite engine` | Частину процесів можна досліджувати як rewrite-like; scope, anuvṛtti, винятки та конфлікти мають бути явними evidence fields. |
| `rule = function` | Rule може бути machine representation лише після опису умови, носія, наслідку, порядку та джерела. |

### `kAraka` і semantic graph

| Небезпечна формула | Допустима формула |
| --- | --- |
| `kartf = subject` або `karman = object` | Це сучасні наближення, непридатні як визначення Panini. |
| `kAraka` автоматично є графовим edge | `[MY-LISP HYPOTHESIS]` edge є одним зі способів подати relation; causative stress test уже показує, що плоскі edges можуть втрачати залежність між учасниками. |

Див. [causative stress test](causative-karaka-stress-test.md).

## Правила редактури

1. Перед computational словом ставити один із трьох маркерів рівня.
2. Для `[PANINI]` додавати sūtra і, якщо твердження сильніше за буквальний
   текст, коментар або сучасне дослідження.
3. Для `[INTERPRETATION]` називати автора, видання або revision implementation.
4. Для `[MY-LISP HYPOTHESIS]` вказувати, що саме можна спростувати тестом або
   повним derivation trace.
5. Не заміняти ім'я сутності аналогією: `it`, `saMjYA`, `kAraka` та
   `pratyAhAra` зберігають SLP1 IDs незалежно від проектного представлення.

## Висновок

Computational vocabulary лишається корисним, якщо його явно позначено як
інтерпретацію або гіпотезу. Фундамент повинен бути місцем, де аналогії стають
перевірюваними, а не місцем, де вони маскуються під джерела.
