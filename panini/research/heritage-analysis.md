# Sanskrit Heritage Platform — code-level audit

Статус: v0.1 (`PANINI-HERITAGE-AUDIT`).

Джерело: `darkone23/Heritage_Platform` (GitHub-дзеркало офіційної
Sanskrit Heritage Platform, Gérard Huet & Pawan Goyal, INRIA;
оригінал розробляється поза GitHub). Мова — OCaml. Прочитано напряму
через `gh api` 2026-08-13: `ML/automaton.ml`, `ML/segmenter.ml`
(перші ~40-60 рядків кожного, включно з докладними doc-коментарями
авторів), повний список файлів `ML/`.

## What Heritage models

- **Сегментація речення з sandhi** — головна задача, якої Vidyut
  (`vidyut-prakriya`) взагалі не вирішує: розібрати неперервний
  санскритський текст (де слова злиті через звукові зміни на межах)
  на окремі словоформи. Vidyut натомість *генерує* одну задану форму
  покроково (`Bavati` з `BU`+`Sap`+`tip`) — Heritage вирішує обернену
  задачу: *з готового тексту* відновити, які форми в ньому є.
- **Морфологія** — відмінювання (`declension.ml`, `nouns.ml`),
  дієвідміна (`conjugation.ml`, `verbs.ml`) — тут функціонально
  перетинається з Vidyut.
- **Зовнішнє sandhi** як окрема, явно виділена підсистема
  (`sandhi.ml`, `sandhier.ml`, `int_sandhi.ml`) — правила з'єднання
  звуків на межах слів, критичні саме для сегментації (яких Vidyut
  торкається значно менше, оскільки генерує ізольовані форми).
- **Лексикон** як inflected trie — попередньо обчислена структура
  всіх словоформ мови (не лише коренів), організована для швидкого
  пошуку префіксів.

## How it models it

- **Автомат, побудований з trie + недетермінізм для sandhi**
  (`automaton.ml`, doc-коментар автора): "Generalises the structure of
  trie... into the graph of a non-deterministic automaton, chaining
  external sandhi with recognition of inflected forms." Детерміноване
  ядро (trie з усіх словоформ) доповнене "choice points" — точками
  недетермінованого вибору, де може спрацювати правило sandhi,
  дозволяючи парсеру перемикатись між "продовжити читати поточне
  слово" і "тут може закінчуватись слово + починається sandhi".
- **Backtracking-парсер зі стеком**: явно згадується "A stack of
  (choices, input_index) permits to backtrack on input failure" —
  Heritage передбачає, що перший знайдений розбір може виявитись
  неправильним (лексична неоднозначність — звичайна річ у
  санскритському реченні без пробілів), і явно підтримує повернення
  назад для пошуку альтернативних сегментацій.
- **"Eilenberg machine"** (`segmenter.ml`) — узагальнений
  скінченний автомат (за традицією Семюеля Айленберга, теоретика
  автоматів) із явними *фазами* (`Phases.phase`) — сегментація не
  єдиний прохід, а послідовність фаз (окремо `aa_phase`,
  `preverb_phase`, `ii_phase` тощо — різні типи sandhi обробляються
  різними фазами конвеєра).
- **Дві окремі стратегії сегментації для різних цілей**: власний
  коментар коду прямо каже — `Segmenter` (лінійний, зі стеком
  backtracking) використовується `Reader`/`Parser`, тоді як
  `Graph_segmenter` (інша структура — граф, не стек) використовується
  окремим `Interface`. Тобто сам Heritage визнає: немає єдиної
  "правильної" структури даних для сегментації, вибір залежить від
  того, що саме потрібно (послідовний розбір vs. інтерактивний
  інтерфейс з переглядом альтернатив).

## What corresponds directly to Pāṇini

- Зовнішнє sandhi (`sandhi.ml`) — це прямий обчислювальний аналог
  фонологічного шару Aṣṭādhyāyī (сандгі-правила з розділів 6, 8),
  того самого шару, що обговорюється в
  `reference-from-engineer-1/PANINI-GRAMMAR-REFERENCE.md` §6.
- Морфологічні модулі (`declension.ml`/`conjugation.ml`) відповідають
  тим самим `sup`/`tiN`-`pratyaya` системам, що й у
  [`pratyaya.md`](../sastra/pratyaya.md).

## What is implementation machinery

- **Trie як структура даних для швидкого пошуку** — суто інженерне
  рішення для продуктивності, не Paninian факт.
- **OCaml-специфічні деталі**: `.mli`-інтерфейси, модульна параметризація
  (`Segment (Phases: ...) (Eilenberg: ...) = struct ... end` —
  functor-стиль OCaml) — конкретна мовна ідіома, не має стосунку до
  граматики.
- **CGI-інфраструктура** (`*_cgi.ml`, `web.ml`, `web_corpus.ml`) —
  веб-інтерфейс платформи, повністю поза обсягом нашого дослідження.

## What we could reuse (як ідею)

- **Явне визнання недетермінізму й багатозначності сегментації** —
  на відміну від Vidyut (де кожна деривація дає один конкретний
  результат для конкретного заданого входу), Heritage будований
  навколо того, що *той самий текст може розбиратись кількома
  способами*, і забезпечує backtracking для пошуку альтернатив. Якщо
  `panini-machine-model-v0.1` колись матиме справу з *аналізом*
  (а не лише генерацією) санскритського тексту, ця архітектурна
  установка — явний недетермінізм, не прихований — варта наслідування
  більше, ніж лінійний imperative-конвеєр Vidyut.
- **Розділення "generation" (Vidyut) і "parsing/segmentation"
  (Heritage) як принципово різних задач** із різними природними
  структурами даних (детермінований журнал кроків vs. недетермінований
  автомат зі стеком) — важливий концептуальний висновок для власного
  майбутнього проєктування: не намагатись знайти "одну структуру для
  всього".

## What we should NOT reuse

- Trie-based повний лексикон усіх словоформ мови (не лише коренів) —
  це рішення оптимізоване для *швидкості пошуку в готовому тексті*,
  зовсім інша мета, ніж наша (дослідження структури граматики). Не
  релевантно для `panini-foundation`.
- CGI/web-специфічна інфраструктура — поза обсягом.
- OCaml functor-параметризація — мовна ідіома, не концепція, яку
  варто "переносити" в Lisp (там є власні природні способи параметризації).

## Порівняння з Vidyut (`PANINI-VIDYUT-AUDIT`)

| | Vidyut (`vidyut-prakriya`) | Sanskrit Heritage |
|---|---|---|
| Основна задача | Генерація: дано `dhAtu`+граматичні ознаки → одна форма | Сегментація: дано текст → можливі розбори |
| Структура деривації | Лінійний журнал кроків (`Vec<Step>`) | Недетермінований автомат + backtracking-стек |
| Ставлення до неоднозначності | Немає — вхід повністю специфікує вихід | Центральна проблема — явно підтримується множинність розборів |
| Мова реалізації | Rust | OCaml |

Обидва — серйозні, довготривалі проєкти тієї самої предметної області,
але розв'язують **обернені задачі** одна до одної. Разом вони
показують два краї спектра "генерація ↔ аналіз", в якому в майбутньому
доведеться визначитись і нашому проєкту.
