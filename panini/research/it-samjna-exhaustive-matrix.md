# Матриця `it-saMjYA`: 1.3.2–1.3.9

## Межа документа

Це evidence matrix для `panini-foundation-v0.1`. Вона описує лише умови
надання `it`-saMjYA та наслідок 1.3.9. Вона не є алгоритмом parser-а, не
встановлює структуру Rust-тегів і не прирівнює `it` до compiler metadata.

Канонічний ID: `it`; display IAST: *it*.

### Інваріанти для trace

1. Термін має зберігати окремо `upadeSa` та поточну видиму форму; інакше
   неможливо довести застосовність 1.3.2–1.3.8 після `lopa`.
2. Кожна мітка повинна містити `sutra`, позицію, class term-а й виняток,
   якщо його перевіряли.
3. `lopa` має посилатися на вже встановлену `it`-saMjYA; не дозволено
   видаляти символ лише тому, що його вважає технічним реалізація.

Приклад лише структури trace (не повна derivation):

```yaml
term:
  upadesha: "..."
  visible_before_lopa: "..."
it_designations:
  - sutra: "1.3.3"
    position: final_hal
    status: asserted
  - sutra: "1.3.4"
    status: checked_exception
lopa:
  sutra: "1.3.9"
  input_designation: "1.3.3"
```

## [INTERPRETATION]

Традиційна практична мова часто каже «marker letters are deleted». Це
скорочення небезпечне: 1.3.9 не робить довільний технічний marker `it`; він
працює після правил saMjYA. Тому два однаково написані символи можуть мати
різний статус залежно від `upadeSa`, позиції, типу term-а і винятку.

Висновок для системи даних: `it` — це не один булевий прапорець. Мінімально
потрібні provenance та причина designation. Повна формалізація взаємодії
1.3.5–1.3.8 потребує окремого rule-level audit і не має бути підмінена цією
таблицею.

## Vidyut: межа порівняння

Vidyut корисний як implementation reference, але його internal tags та
поля стану не є новими категоріями Паніні. Порівняння дозволене лише за
такими питаннями:

| Рівень | Допустиме твердження | Недопустиме твердження |
| --- | --- | --- |
| Дані терма | Реалізація може зберігати upadeśa й поточний текст окремо. | Поле Rust автоматично є панініївською saMjYA. |
| Позначення | Реалізація може фіксувати наслідок конкретного sūtra. | Будь-який runtime tag є `it`. |
| Видалення | Технічна операція може реалізувати наслідок 1.3.9. | Технічне видалення саме доводить застосування 1.3.9. |

Конкретні назви Vidyut API слід додавати лише з revision-pinned code audit;
цей документ їх навмисно не вигадує.

## Аудит наявного `panini/machine`

Поточні machine-прототипи мають розглядатися як [MY-LISP HYPOTHESIS], не як
джерело Panini. Для наступного review вони мають щонайменше такі ризики:

- тег на кшталт `p-it` або `S-it` без `sutra` і позиції не зберігає доказ,
  чому символ набув `it`-saMjYA;
- виведення граматичної категорії, наприклад `sArvaDAtukaM`, прямо зі знака
  `it` зливає різні saMjYA та потребує окремих sūtra;
- правило «видалити відомі літери» не замінює послідовності
  designation → перевірка винятку → 1.3.9 `lopa`;
- таблиця допустимих `hal` не може бути коротким довільним переліком, якщо
  вона претендує реалізувати `halantyam`.

Це не є вимогою змінити machine-код у Phase 1. Це список блокерів для будь-якої
майбутньої заяви про paninian correctness.

## [MY-LISP HYPOTHESIS]

Якщо після Foundation v0.1 з'явиться машинна модель, безпечний мінімум —
представити `it` як provenance-bearing designation, а `lopa` як окремий
trace step. Конкретні struct, tag name, VM instruction чи оптимізація —
проектне рішення, яке не може бути назване Panini без окремого доказу.
