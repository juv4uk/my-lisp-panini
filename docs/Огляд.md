# Огляд `my-lisp-panini`

**Об’єкт:** [`juv4uk/my-lisp-panini`](https://github.com/juv4uk/my-lisp-panini)  
**Метод:** огляд структури репозиторію, формальних специфікацій, machine-коду, acceptance fixtures, registry-моделі та координації з `shiva-sutras`.  
**Головний висновок:** `my-lisp-panini` не намагається зробити з Паніні «раннього Lisp». Він формує **проміжний шар між джерелами та обчислювальною моделлю**: knowledge compiler, що несе не тільки форми й правила, а й межі їхньої доказовості.

## 1. Найкраще формулювання проєкту вже є в README

> **A formal foundation before a hypothesis.** [1]

Це дуже точна назва того, що ти робиш. Проєкт не стартує з мапи на кшталт `saṃjñā = type`, `anuvṛtti = lexical closure`, `kāraka = graph edge` або `it = compiler metadata`. Спершу він фіксує, що засвідчують sūtra і джерела; потім показує, як це інтерпретується; лише на третьому рівні додає обмежену machine hypothesis.

У `panini-foundation-v0.1.md` ця дисципліна є не стилем prose, а конструкцією специфікації: кожне складне поняття проходить через `[PANINI]`, `[INTERPRETATION]` і `[MY-LISP HYPOTHESIS]` [2]. Це — пряме продовження епістемічної культури `shiva-sutras`, але з іншим завданням: upstream встановлює статус знання про Śiva-sūtras, а Panini-шар будує підконтрольну формальну модель граматики.

## 2. Архітектурне місце в екосистемі

```text
shiva-sutras
  authoritative claims: canon, pratyāhāra, markers, evidence, scope
                 ↓
my-lisp-panini
  knowledge compiler: ontology, registry, derivation IR, machine fixtures
                 ↓
my-lisp
  semantic substrate: values, rules, inference, proof, immutable Worlds
                 ↓
CML / fpga-lisp
  independent execution boundary
```

Це правильна послідовність. `my-lisp-panini` не дублює роль `shiva-sutras` і не намагається самовільно зробити історичні висновки. Одночасно він не вбудовує Паніні безпосередньо в Rust evaluator або VM `my-lisp`: його `bridge-to-my-lisp.md` прямо оголошує це **research boundary**, а не інтеграційним планом [3].

| Шар | Що він володіє | Чого він не повинен робити |
|---|---|---|
| `shiva-sutras` | Claims, provenance, scope, статус математичних і джерелознавчих результатів | Давати downstream реалізаційні поради. |
| `my-lisp-panini` | Онтологію, registry, derivation IR, evidence model і machine fixtures | Оголошувати машинну аналогію історичним фактом. |
| `my-lisp` | Маленьку мову, reasoning, journals, Worlds та execution semantics | Приймати панінійський термін як primitive без окремого contract. |

## 3. Формальна модель: дуже хороше трирівневе розділення

Foundation v0.1 розрізняє три категорії сутностей [2]:

| Рівень | Приклади | Значення для реалізації |
|---|---|---|
| **Object language** | `dhAtu`, `prAtipadika`, `pratyaya`, `kAraka` | Те, що описує санскритську мову та її учасників. |
| **Metalanguage** | `saMjYA`, `it`, `pratyAhAra`, `aDikAra`, `anuvftti` | Апарат, який керує читанням і застосуванням граматики. |
| **Rule system** | `sUtra`, `paribhAzA`, `vipratiSeDa`, `utsarga/apavAda` | Умови, переходи, meta-rules і політики конфлікту. |

Це розділення запобігає класичній помилці: вважати технічний маркер `it` або позначку `pratyāhāra` частиною поверхневого результату. SLP1 при цьому використовується як canonical machine identifier, а IAST і Devanāgarī — лише для display, що є правильним рішенням для реєстрів, fixtures та serializable IR [2].

Найважливіше: слово `rule` тут не означає «функція host-мови». Специфікація вимагає, щоб правило було декларативним об’єктом із ID, умовами, дією та джерелом. Це дуже добре стикується з `my-lisp`, бо робить правило даними, які можна показати, порівняти, прив’язати до evidence і покласти в proof trace.

## 4. Derivation IR — найсильніший технічний артефакт

`derivation-ir-v0.1.md` — це не просто ще один YAML schema. Це спроба побудувати **машинний слід деривації, який не втрачає різницю між джерелом, інтерпретацією, machine rule і результатом** [4].

IR має immutable states, typed terms, declared rule references, explicit operations, append-only trace, provenance та status `success | partial | blocked | invalid`. Важливі guardrails виглядають так:

| Guardrail | Чому він важливий |
|---|---|
| `sutra-reference` не може мати executable operation сам лише через номер sūtra | Запобігає магічному перетворенню цитати на алгоритм. |
| Executable operation дозволена лише для `machine-rule` з interpretation/implementation provenance | Робить інженерне припущення явним. |
| `opaque` operation примусово знижує результат до `partial` | Невідоме не маскується як завершена деривація. |
| Machine metadata має namespace | `machine:dhatu` не видається за панінійський `dhAtu`. |
| Kāraka relation потребує окремого provenance | Graph edge — це модель, а не автоматично факт тексту. |
| State hash вираховується з canonical content | Історія деривації стає порівнюваною та відтворюваною. |

Це дуже близько до того, що ти називаєш proof-carrying derivation. Не «ось фінальний рядок», а «ось конкретні стани, чому був обраний rule, що змінилося і де закінчується наша впевненість».

## 5. Machine layer уже живий, але чесно вузький

Виконуваний шар у `panini/machine/` не удає повноцінний engine Aṣṭādhyāyī. Він реалізує вузькі, явні й перевірювані fixtures [5] [6].

`panini-core.my` тримає registry kāraka та dhātu. Важлива деталь: dhātu YAML registry названий authoritative source, а Lisp-завантаження — test snapshot. Це правильне single-source правило. Kāraka membership є situation-scoped, містить provenance і status, тому `devadatta` або `pac` не отримують вічну «роль агента» просто з прикладу [5].

`rules.my` містить `Bavati`, `dadAti`, `karoti` і `pacati` як окремі bounded fixtures. Найкращий із них — `Bavati`: він має 7 state transitions, але навмисно завершується як `partial`, а не як `success`, і виводить список конкретних невідомих preconditions. Це значно цінніше за демо, яке просто друкує правильну поверхневу форму [6].

> **Спостережений результат не дорівнює доведеній повній деривації.**

Саме цю різницю багато symbolic systems втрачають. Тут вона закодована в самій fixture-моделі.

## 6. Тести перевіряють не тільки «успішні слова»

`panini/machine/tests.my` містить перевірки pratyāhāra, guṇa, sandhi, registry loading, canonical SHA-256 state vectors, `utsarga/apavāda`, anuvṛtti DAG edges і situated kāraka membership [7]. Але його найбільш здоровий аспект — negative fixtures:

- `it` не видаляється без marker tag;
- `guṇa` не застосовується до неeligible sound;
- некоректний SLP1 glyph відхиляється;
- `Śap` не вставляється у неприпустимий клас без належного попереднього переходу;
- взаємно суперечливі `apavāda` priority declarations позначаються ambiguous;
- `Bavati` має перевірений `partial` status і explicit unknowns.

Тобто тест проходить не тоді, коли система випадково отримала знайомий surface string, а коли вона також відмовилася робити непідтверджений крок. Для майбутнього agent system це правильна модель acceptance.

## 7. Що особливо добре в координації з `shiva-sutras`

Тут збережена потрібна асиметрія. `shiva-sutras` експортує qualified claims з ID, status, evidence, scope та limitations. `my-lisp-panini` споживає їх як input до власної моделі, але не може перетворити `SUPPORTED` на `PROVED`, а `PROVED-IN-MODEL` — на історичне твердження [3] [8].

Це означає, що Panini-шар може використовувати `SS-PRATYAHARA-001` для пояснення механіки, але не мусить робити висновок «pratyāhāra є bitmap», доки той є лише implementation choice. Такий контракт робить весь ланцюг набагато надійнішим за підхід, де терміни з філології прямо стають іменами функцій у runtime.

## 8. Що я б зробив наступним

### 1. Зафіксував `derivation-ir-v0.1` як золотий interchange contract

Не поспішати з новими primitives у `my-lisp`. Спершу зробити кілька golden fixtures — наприклад, `Bavati`, `dadAti`, `karoti`, `pacati` — які мають однаковий IR shape: terms, states, candidate rules, selected policy, transition trace, provenance і status. Тоді Rust, my-lisp, Racket reference та майбутня hardware/compiled path зможуть порівнювати не лише surface result, а й доказовий слід.

### 2. Відокремити «fixture, що друкує форму» від «derivation, що пройшла gate»

Ти вже це робиш через `partial`, але можна зробити ще видиміше в README: наприклад, labels `observed surface`, `machine fixture`, `source-supported transition`, `complete derivation`. Тоді зовнішній читач не сприйматиме `Bavati` як заяву, що вся історична процедура вже formalized.

### 3. Автоматизувати import claims із `shiva-sutras` у read-only режимі

Замість копіювати необхідні параметри, зробити manifest dependency на `SS-*` IDs із pinned revision і мінімальним допустимим статусом. Це вже закладено в upstream-contract; Panini може перетворити його на registry check перед запуском fixture. Якщо upstream claim змінюється, derivation отримує `blocked` або `needs-review`, а не непомітно продовжує працювати на старому припущенні.

### 4. Оновити кілька історичних посилань після реорганізації directory tree

Поточна clone-структура не містить `panini/foundation/`, хоча `panini-foundation-v0.1.md` досі показує цей каталог як фінальну v0.1-tree і містить посилання на його старі шляхи. Оскільки репозиторій уже був реорганізований у `panini/{machine,registry,research,sastra,specs,...}`, короткий supersession note або redirects у spec зроблять його простішим для нового агента й нового читача. Це документаційна гігієна, не зміна моделі.

## Фінальний погляд

`my-lisp-panini` я бачу як **місце, де твої абстракції проходять перевірку на епістемічну тверезість**. `my-lisp` каже: можна мати rules, proof, history, data-only exchange і Worlds. `shiva-sutras` каже: знання має scope, source, status і право лишатися unresolved. `my-lisp-panini` з’єднує ці дві вимоги на складному реальному предметі.

Тому найкраща річ у ньому — не `guṇa` і не YAML registry самі по собі. Це правило: **не вважати зрозумілий тобі computational model достатньою підставою, щоб назвати його Паніні.** Якщо ти збережеш саме цю стриманість, Panini-шар зможе дуже природно стати першим справді глибоким stress test для proof-carrying knowledge в `my-lisp`.
